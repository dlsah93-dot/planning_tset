상태: **EPIC 1 완료 / EPIC 2 구현·자동 검사 통과, 사용자 확인 대기 / EPIC 3 기능 미착수, 배포만 별도 완료**

아래 1~5절은 EPIC 1의 검사와 사용자 승인 기록이다. 이번 EPIC 2 결과는 6절에 추가한다.

## 1. 범위와 검사 환경

기준은 `docs/01_PRD.md`, `docs/02_FRD.md`, `docs/03_TRD.md`, `docs/04_개발계획.md`와 `design`의 판매 목록·판매 입력·메뉴 수익성·재고 시안이다. 시안에만 있는 POS 연동·시간대·임시 저장·CSV·발주 등은 추가하지 않았다. 이 작업에서는 EPIC 1의 S01~S05만 구현했다.

- 실행 주소: `http://127.0.0.1:5173/`.
- 화면: 판매 기록 관리, 메뉴 수익성, 재료 잔량과 변동 내역.
- 실제 저장: IndexedDB `prep-cafe-operations`, 구조 버전 1. 브라우저·주소가 같을 때 재접속 후 기록을 읽는다.
- 자료: 제공 JSON과 동일한 가상 샘플 1개. 업무 기록 11묶음·총 11,852개. 원본 판매 6,112개, 재고 기록 1,515개. 엑셀을 중복 초기 입력하지 않았다.
- 실행 환경: Windows, Node.js 24.19.0. 라이브러리 정확한 버전은 `package-lock.json`에 고정했다.
- 계산·저장 검사: Vitest 5.0.3, fake-indexeddb 6.2.5.
- 실제 브라우저 자동 검사: Playwright 1.64.0, Chromium 156.0.8078.4. 각 검사는 별도 임시 브라우저 자료를 사용해 사용자의 확인용 브라우저 자료와 분리했다.
- 화면 크기: 자동 검사에서 1440×1000 및 390×844 확인.
- 직접 확인용 브라우저: Codex 내장 브라우저에 실행 주소를 열었다. 초기 자료가 표시되는 실제 DOM을 확인했다. 이 확인은 담당자의 검사이며 사용자 확인을 대신하지 않는다.

기간 손익·비용 입력·입고·폐기 입력은 EPIC 2, 실제 재고 입력·백업·복원과 GitHub/Vercel 운영 배포는 EPIC 3이다. 기존 자료의 입고·폐기·실사 기록은 EPIC 1 잔량 계산에서 실제 반영한다.

### 확인한 숫자

- FRD 계산 예제: 매출 38,000원, 수수료 570원, 개당 식재료 원가 460원일 때 남는 금액 32,830원, 이익률 86.4%.
- 제공 자료의 2026년 9월 전체 채널: 256개 판매 집계 기록, 판매수량 2,956개, 순매출 13,968,930원, 메뉴에서 남는 금액 표시 10,212,723원. 합계 원가를 중간 반올림하지 않고 마지막 표시에서 반올림한다.
- 2026-10-12 아메리카노 매장 판매 예시: 10개×4,000원−할인 2,000원 = 순매출 38,000원, 수수료 570원. 적용 개당 식재료 원가 496.8원, 식재료비 4,968원, 남는 금액 32,462원, 이익률 85.4%. 원두 사용량 200g.
- 직접 확인용 초기 자료의 원두 잔량: 2026-09-18 기준 4,280g. 추가 기록이 없는 2026-10-12도 4,280g이다. 위 판매를 저장하면 4,080g이며 수량 20개로 수정하면 3,880g, 해당 판매를 삭제하면 4,280g으로 돌아온다.
- 실사 검사 예제: 초기 1,000g+입고 500g−사용 400g−폐기 100g 이후 실제 900g을 기준으로 사용하며 다음 날 사용 200g 후 잔량은 700g. 과거 판매 변경으로 실제 900g을 덮어쓰지 않는다.

## 3. 발견한 문제와 수정·재검사

| --- | --- | --- |

최종 자동 검사에서 실패한 항목은 없다. 용량 부족은 저장 실패를 주입해 거래 보존을 검사했으며 실제 사용자 기기의 저장공간을 소진시키지 않았다. 사용자 확인은 아래 전체 승인에 따라 통과 처리했다. 운영 배포 검사는 아직 수행하지 않았다.

## 6. EPIC 2 — 구현·검사 결과 (2026-10-12)

### 6.1 구현한 범위

S06 비용 입력, S07 비용 수정·삭제, S08 일·월 실적과 손익, S09 입고, S10 폐기를 구현했다. 기존 판매·메뉴 수익성·잔량과 같은 저장 자료를 사용한다. 실제 재고 입력·백업·복원·운영 배포 등 EPIC 3은 착수하지 않았다.

| 기능 | 처리와 화면 결과 |
| --- | --- |
| 비용 관리 | 귀속일·기존 8개 항목·양의 정수 금액으로 입력. 정상적인 쉼표 금액 허용. 같은 귀속일·항목은 중복을 막고 기존 합계 수정 안내. 원본 배분기준은 보존하고 신규 기록은 ‘직접 입력’ |
| 비용 정정 | 날짜·항목·금액 수정, 확인 후 삭제. 비용과 기간 손익만 바뀌고 메뉴 수익성·재고는 유지. 마감 날짜 변경은 재확인 필요 표시 |
| 기간 손익 | 전체 판매 채널의 순매출·메뉴에서 남는 금액·운영비·기록 기준 손익. 실제 기록 포함 기간, 확정 일평균, 날짜별 마감·휴무·미마감·마감 정보 없음·변경 후 확인 필요 표시 |

| 음수 폐기 | 기록일 또는 최근 기록일 잔량이 음수면 별도 확인 전 저장하지 않음. 승인하면 음수 경고와 함께 저장. 폐기 손실·구매비용 자동 추가 없음 |
| 저장·실패 | 입력 검증·계산 후 기록·재확인 상태·변경번호를 함께 저장. 실패하면 모두 보존하고 입력창 유지. 다른 창 변경 시 새로고침 안내. 저장 버튼 중복 클릭 방지 |

### 6.2 실제 자동 검사

| 검사 | 실행 결과 | 주요 확인 내용 |

최종 검사 합계는 **57개 통과**다. 첫 브라우저 검사에서는 메뉴 이익 비교의 줄바꿈 처리 때문에 1개가 실패했다. 금액은 일치했으며, 검사에서 같은 텍스트 읽기 방식을 사용하도록 고친 후 전체 11개를 다시 실행해 통과했다. 실제 사용자 확인 결과로 바꾸어 기록하지 않았다.

빌드에 JavaScript 파일 크기가 500kB를 넘는다는 참고 경고가 있었다(약 511kB, 압축 약 158kB). 빌드는 성공했다. 최종 브라우저 검사에서 최초 샘플 준비는 약 1.3초였으며 모든 기기의 속도를 보장하는 수치는 아니다.

자동 검사는 사용자 브라우저와 분리된 임시 자료를 사용했다. 담당자가 사용자 확인용 내장 브라우저의 `/#/dashboard`를 열고 2026-09 월간 자료를 직접 읽었다. 이때 자료 변경번호는 0이었고 입력·삭제를 수행하지 않았다. 화면 증거: [기간 손익](evidence/epic2-dashboard.png).
