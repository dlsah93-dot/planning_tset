# 카페 판매·손익·재고 관리 개발 계획

작성일: 2026-10-12  
상태: EPIC 1은 2026-10-12 사용자의 전체 확인 항목 통과 승인으로 완료 처리했다. EPIC 2는 구현·자동 검사 통과 후 사용자 확인 대기다. EPIC 3은 미착수다. 검사 결과와 승인 근거는 `docs/05_테스트결과.md`에 기록한다.

## 1. 전체 작업 순서와 나눈 이유

EPIC은 함께 개발할 작업 묶음이고, User Story는 사용자가 한 가지 목적을 달성하는 기능 단위다. 1차 개발은 **3개 EPIC, 13개 Story**로 구성한다.

| 순서 | EPIC | Story 수 | 실제 화면에서 확인할 결과 | 현재 상태 |
| --- | --- | ---: | --- | --- |
| 1 | 판매 기록과 메뉴 수익성·잔량 확인 | 5 | 판매를 기록하면 메뉴 수익성과 재료 잔량이 바뀜 | 완료 · 2026-10-12 사용자 승인 |
| 2 | 운영비·재료 변동과 기간 손익 확인 | 5 | 비용·입고·폐기를 반영한 일·월 손익과 잔량을 확인함 | 구현·자동 검사 통과 / 사용자 확인 대기 |
| 3 | 실제 재고 기록과 백업·복원 | 3 | 직접 센 수량을 기준으로 잔량을 관리하고 전체 기록을 복원함 | 미착수 |
| 합계 | EPIC 3개 | 13 | 판매 입력부터 손익·재고 확인, 기록 보존까지 연결됨 | 완료 EPIC 1개 |

판매·재고의 계산과 저장을 먼저 만들고, 운영비를 연결한 뒤 전체 기록을 백업한다. 백업·복원은 앞 단계의 모든 자료가 갖춰져야 제대로 검사할 수 있어 마지막에 배치한다.

기준 문서는 `docs/01_PRD.md`, `docs/02_FRD.md`, `docs/03_TRD.md`와 `design`의 시안이다. PRD의 1차 범위, FRD의 기능·계산·예외 기준, TRD의 구현 방법을 변경하지 않는다. 정상적으로 볼 수 없는 시안 PNG는 해당 HTML과 FRD를 기준으로 구현한다.

엑셀 양식·가져오기, 주·분기·반기·연간 조회, 예상 손익, 부족 판단·발주 참고량 등 기존 문서의 2차 기능은 이번 개발 대상에서 제외한다.

## 2. EPIC 1 — 판매 기록과 메뉴 수익성·잔량 확인

**포함 Story: S01~S05 / 상태: 완료 — 구현·자동 검사 통과, 2026-10-12 사용자 전체 통과 승인**

첫 실행 시 자료를 준비하고, 판매 입력 → 메뉴 수익성 → 재료 잔량으로 이어지는 흐름을 완성한다. 기존 자료의 입고·폐기·실제 재고도 처음부터 잔량 계산에 반영한다. 공통 계산·검증·저장은 각 기능을 실제로 동작시키는 기반 작업으로 포함한다. 기간 손익 화면과의 최종 연결 검사는 EPIC 2에서 수행한다.

### S01. 기존 판매 기록을 찾아본다

- **사용자가 할 수 있는 일:** 처음 접속해 제공 자료의 판매 기록을 확인하고, 날짜·메뉴·판매 채널 등 FRD의 조건으로 원하는 기록을 찾는다.
- **자동 검사:** 처음 실행할 때만 자료를 저장하고 재접속 시 중복 생성하지 않는지 검사한다. 검색·기간·페이지 이동 결과, 전체 조회 합계와 현재 페이지의 구분을 검사한다. 자료 연결이 잘못되면 정상 준비 상태로 표시하지 않는다.
- **화면 확인 행동과 예상 결과:** 판매 목록에서 기간과 메뉴를 바꾼다. 조건에 맞는 기록과 합계가 나오고 새로고침해도 같은 자료가 유지된다. 검색 결과가 없으면 빈 목록임을 안내한다.

### S02. 새 판매를 기록한다

- **사용자가 할 수 있는 일:** 날짜·메뉴·매장/포장·수량·가격·할인·수수료를 입력해 판매를 저장한다.
- **자동 검사:** 매출·수수료·판매 당시 원가·재료 사용량을 FRD대로 계산한다. 잘못된 날짜·수량·할인·수수료와 중복 기록을 차단한다. 원가 기준 누락, 음수 재고 안내, 중복 클릭과 저장 실패를 검사하며 기록과 계산 결과가 일부만 바뀌지 않아야 한다.
- **화면 확인 행동과 예상 결과:** 기록이 없는 날짜·메뉴·채널 조합에 수량 10개, 가격 4,000원, 할인 2,000원, 수수료 1.5%를 입력한다. 매출은 38,000원, 수수료는 570원으로 기록된다. 해당 날짜의 원가와 레시피에 따라 수익성과 잔량이 바뀌고 재접속해도 기록이 남는다.

### S03. 잘못된 판매 기록을 정정한다

- **사용자가 할 수 있는 일:** 잘못 입력한 판매를 수정하거나, 실제로 발생하지 않은 판매를 삭제한다. 두 동작은 잘못된 판매를 바로잡는 하나의 목적이며 각각 검사한다.
- **자동 검사:** 수정·삭제가 매출·수익성·재고에 한 번만 반영되는지 검사한다. 수정 항목별 원가·수수료 유지 및 재계산, 변경 없는 저장, 과거 마감일의 ‘재확인 필요’ 표시를 FRD대로 검사한다. 취소·중복·저장 실패 시 원래 기록을 유지한다.
- **화면 확인 행동과 예상 결과:** 판매 수량을 바꾸면 목록·수익성·잔량이 함께 바뀐다. 삭제 확인을 취소하면 그대로 남고, 삭제를 확정하면 해당 판매의 영향이 제거된다.

### S04. 메뉴별로 남는 금액을 확인한다

- **사용자가 할 수 있는 일:** 기간과 판매 채널을 선택해 메뉴별 판매량·매출·원가·수수료·남는 금액을 비교하고 정렬한다.
- **자동 검사:** 판매 당시 원가와 실제 기록된 수수료, 판매량을 고려한 평균과 수익률을 검사한다. 중간 원가를 임의 반올림하지 않고 FRD의 표시 기준을 따른다. 판매 없음·매출 0·적자 메뉴와 전체 합계의 일치를 검사한다.
- **화면 확인 행동과 예상 결과:** 판매를 저장한 기간을 선택한다. 해당 메뉴 실적이 표시되고, 매장/포장을 바꾸면 적용되는 포장재와 수익성 차이를 확인할 수 있다. 계산할 수 없는 비율은 사유와 함께 표시된다.

### S05. 재료 잔량과 변동 내역을 확인한다

- **사용자가 할 수 있는 일:** 기준일을 선택하고 재료·공급처를 찾아 잔량, 단위, 최근 실제 재고와 변동 내역을 확인한다.
- **자동 검사:** 초기 재고·판매 사용량·입고·폐기·실제 재고를 날짜와 FRD의 적용 순서대로 반영한다. 실제 재고 이후의 잔량, 음수 잔량, 레시피·기준자료 누락을 검사한다. 실제 재고 차이를 이중 반영하지 않는다.
- **화면 확인 행동과 예상 결과:** 판매 전후의 기준일을 조회하면 사용한 재료만 필요한 양만큼 줄어든다. 음수 잔량은 경고로 표시되고 계산에 필요한 자료가 없으면 계산 불가 사유가 나온다. 기존 실제 재고 이후 잔량은 실제 수량을 기준으로 이어진다.

### EPIC 1 완료 기준

- 제공 자료가 실제 저장되고 재접속 후 유지된다.
- 판매 추가·정정이 메뉴 수익성과 재료 잔량에 정확히 연결된다.
- 취소·잘못된 입력·저장 실패로 기존 자료가 훼손되지 않는다.
- 판매·수익성·재고 화면이 실제 자료로 동작한다.
- 자동 검사를 통과하고, 사용자가 해당 화면의 확인 행동을 문제없이 수행했다고 확인한다.

## 3. EPIC 2 — 운영비·재료 변동과 기간 손익 확인

**포함 Story: S06~S10 / 선행: EPIC 1 / 상태: 구현·자동 검사 통과 — 사용자 확인 대기**

운영비와 재료 변동을 직접 기록하고 매장 전체의 일·월 실적과 손익을 확인한다.

### S06. 운영비를 기록한다

- **사용자가 할 수 있는 일:** 비용이 발생한 날짜·분류·금액을 입력해 운영비를 저장한다. 시안의 금액 추가 버튼은 입력값만 바꾼다.
- **자동 검사:** 비용이 지급일이 아닌 발생일에 반영되는지 검사한다. 날짜·분류·금액과 같은 날짜·분류의 중복을 검사하며 중복 비용은 기존 기록 정정으로 안내한다. 월 비용 계획을 다시 차감하지 않는다. 실패 시 기존 자료를 유지한다.
- **화면 확인 행동과 예상 결과:** 기존 비용과 중복되지 않는 조합에 새로운 비용 10,000원을 입력한다. 해당 기간 비용이 10,000원 늘고 손익은 같은 금액만큼 줄어든다. 메뉴 수익성과 재료 잔량은 바뀌지 않는다.

### S07. 잘못된 운영비를 정정한다

- **사용자가 할 수 있는 일:** 비용의 날짜·분류·금액을 수정하거나 잘못된 비용을 삭제한다. 두 동작은 잘못된 비용을 바로잡는 목적이며 각각 검사한다.
- **자동 검사:** 금액 변경과 날짜 이동이 해당 기간에 정확히 반영되는지 검사한다. 중복·잘못된 입력·삭제 취소·저장 실패 시 원래 자료를 보존한다. 과거 마감 자료 변경 상태는 FRD대로 처리한다.
- **화면 확인 행동과 예상 결과:** 비용 10,000원을 15,000원으로 수정하면 비용이 5,000원 늘고 손익이 5,000원 줄어든다. 삭제 확인을 취소하면 기록이 유지되고 확정하면 비용 영향이 제거된다.

### S08. 일·월 실적과 손익을 확인한다

- **사용자가 할 수 있는 일:** 하루 또는 한 달을 선택해 매출·메뉴에서 남는 금액·운영비·매장 손익과 기록 포함 기간을 확인한다.
- **자동 검사:** 판매와 비용의 합계, 메뉴 수익성 화면과의 일치, FRD의 확인된 영업일 평균을 검사한다. 미마감·누락·휴무·재확인 필요 날짜를 구분한다. 월 조회 재고를 합산하지 않고 FRD의 기준일을 사용한다. 판매 추가·수정·삭제와 손익 화면의 연결도 검사한다.
- **화면 확인 행동과 예상 결과:** 판매와 비용을 기록한 기간을 선택한다. 메뉴에서 남는 금액에서 운영비를 뺀 손익이 표시된다. 미마감 날짜나 자료가 없는 날짜는 확정된 0원 실적으로 표시되지 않는다. 2026년 9월 1~18일의 확인된 영업일은 16일로 처리한다.

### S09. 재료 입고를 기록한다

- **사용자가 할 수 있는 일:** 날짜·재료·입고량 등 FRD의 항목을 입력해 들어온 재료를 기록한다.
- **자동 검사:** 날짜·재료·양수 수량, 재료별 단위와 소수 허용 범위를 검사한다. 중복 클릭으로 두 번 저장되지 않고 해당 날짜 이후 잔량에 정확히 반영되는지 검사한다. 저장 실패 시 기존 자료를 보존한다.
- **화면 확인 행동과 예상 결과:** 원두 500g을 입고로 저장한다. 변동 내역에 나오고 이후 잔량이 재고 계산 순서에 맞게 바뀐다. 뒤에 실제 재고 기록이 있다면 그 기준도 유지한다. 잘못된 수량은 저장되지 않는다.

### S10. 재료 폐기를 기록한다

- **사용자가 할 수 있는 일:** 날짜·재료·폐기량·사유를 입력해 버린 재료를 기록한다.
- **자동 검사:** 날짜·수량·단위·필수 사유와 음수 재고 확인 절차를 검사한다. 폐기가 잔량에 한 번만 반영되고 별도의 손실 비용을 자동 추가하지 않는지 검사한다. 취소·저장 실패 시 기존 자료를 유지한다.
- **화면 확인 행동과 예상 결과:** 원두 100g과 폐기 사유를 저장한다. 변동 내역에 표시되고 잔량이 재고 계산 순서에 맞게 반영된다. 음수 재고가 되는 경우에는 FRD의 확인 절차를 거친다.

### EPIC 2 완료 기준

- 비용 추가·정정과 입고·폐기가 저장되고 재접속 후 유지된다.
- 판매 → 메뉴 수익성 → 일·월 손익과 잔량의 전체 흐름을 확인할 수 있다.
- 비용 중복 차감, 재고 이중 반영, 미마감 자료 오해를 막는다.
- 입력 오류·취소·저장 실패 처리가 실제 화면에서 동작한다.
- 자동 검사를 통과하고, 사용자가 해당 화면의 확인 행동을 문제없이 수행했다고 확인한다.

## 4. EPIC 3 — 실제 재고 기록과 백업·복원

**포함 Story: S11~S13 / 선행: EPIC 1·2 / 상태: 미착수**

직접 센 재고를 잔량의 기준으로 기록하고 완성된 전체 자료를 파일로 보관하거나 복원한다.

### S11. 직접 센 재고를 기록한다

- **사용자가 할 수 있는 일:** 날짜·재료·실제로 센 수량·사유를 기록하고 계산상 잔량과의 차이를 확인한다.
- **자동 검사:** 빈 입력과 실제 0을 구분한다. 당일 마지막 실제 재고를 이후 잔량의 기준으로 사용하며 같은 날의 여러 기록과 과거 판매 정정을 FRD대로 처리한다. 실제로 센 수량과 최초 차이는 보존하고 재계산한 차이를 구분한다. 날짜·단위·사유·실패·중복 클릭도 검사한다.
- **화면 확인 행동과 예상 결과:** 계산상 원두가 1,000g인 상태에서 실제 수량 900g을 저장하면 차이 −100g과 잔량 900g이 표시된다. 다음 날 200g을 사용하면 700g이 된다. 과거 기록을 수정해도 직접 센 900g 자체는 바뀌지 않는다. 실제 수량 0도 기록할 수 있다.

### S12. 전체 기록을 백업한다

- **사용자가 할 수 있는 일:** 판매·비용·재고·기준정보·설정 등 FRD의 전체 대상을 하나의 JSON 백업 파일로 내려받는다.
- **자동 검사:** 조회 조건과 관계없이 모든 대상 자료가 포함되는지, 과거 원가·수수료·실제 재고·재확인 상태 등이 유지되는지 검사한다. 백업 중 자료가 바뀌어 서로 다른 상태가 섞이지 않아야 한다. 형식·버전·건수·메타데이터와 생성 오류를 검사한다.
- **화면 확인 행동과 예상 결과:** 일부 기간을 조회한 상태에서 백업한다. 파일에는 전체 기간 자료가 포함된다. 실제 파일 보관 여부는 사용자가 확인하며 프로그램은 다운로드 요청만으로 보관 완료를 단정하지 않는다.

### S13. 백업으로 전체 기록을 복원한다

- **사용자가 할 수 있는 일:** 백업 파일의 검사 결과와 자료 범위를 확인한 뒤 현재 자료를 백업 내용으로 교체한다.
- **자동 검사:** TRD의 50,000,000바이트 제한, UTF-8·형식·버전·매장·날짜·중복·자료 연결을 검사한다. 원본 샘플 JSON을 프로그램 백업으로 오인하지 않는다. 현재 자료 백업과 사용자 보관 확인, ‘복원확인’ 입력을 거쳐야 복원한다. 파일 변경 시 확인 상태를 초기화한다. 취소·실패 시 기존 자료를 보존하고 성공 시 전체 자료·계산·저장을 검사한다.
- **화면 확인 행동과 예상 결과:** 백업 후 판매를 추가하고 이전 백업을 복원한다. 검사 결과 확인 → 현재 자료 백업·보관 확인 → ‘복원확인’ 입력 → 복원 순서로 진행한다. 완료 후 판매·비용·재고가 이전 상태와 일치한다. 잘못된 파일이나 복원 시작 전 취소는 현재 자료를 바꾸지 않는다.

### EPIC 3 완료 기준

- 실제 재고를 기준으로 이후 잔량이 정확히 이어진다.
- 전체 백업과 복원 후 기록·계산 결과가 일치한다.
- 복원 실패로 기존 자료가 일부만 교체되지 않는다.
- GitHub 코드 보관과 Vercel 배포를 완료한다. 운영 주소에서 핵심 흐름, 재접속 후 저장, 백업·복원을 검사한다. 개발 주소와 운영 주소의 자료 보관소가 다르다는 TRD 기준을 따른다.
- 자동 검사를 통과하고, 사용자가 해당 화면의 확인 행동을 문제없이 수행했다고 확인한다.

## 5. 공통 검사와 시간 관리

자동 검사는 계산 검사, 저장·실패 검사, 실제 브라우저 사용 흐름 검사로 구성한다. FRD F01~F13과 C01~C06을 누락 없이 확인하며 TRD의 계산 정밀도·자료 보호·성능·배포 검사 기준을 따른다. 위 항목은 수행할 검사 계획이며 현재 통과했다는 뜻은 아니다.

저장과 계산은 모든 Story에 포함한다. 화면만 만들거나 임시 값·가짜 성공 표시로 완료 처리하지 않는다. 실제 운영 자료를 GitHub나 외부 로그에 올리지 않는 등 TRD의 개인정보 보호 기준도 공통으로 적용한다.

4시간 작업 예산은 기존 문서대로 기획 25분·화면 설계 30분·개발 130분·검사 35분·배포 20분이다. 앞 단계에서 이미 수행한 기획·설계 시간도 전체 예산에 포함한다. 4시간 완료를 보장하지 않으며 시간이 부족해도 필수 기능·저장·계산·검사를 생략하지 않는다. 남은 작업과 추가 소요를 명확히 기록한다.

## 6. 구현·사용자 확인·완료 표시 방법

사용자가 요청한 실행 단위는 아직 완료하지 않은 다음 EPIC 하나다. 문서 저장 자체는 구현 완료가 아니다. EPIC 1은 구현·검사 후 사용자의 전체 통과 승인을 받아 완료했다. 다음 대상은 EPIC 2이며, 이번 승인 기록 작업에서 EPIC 2·3 구현을 시작하지 않는다.

1. 해당 EPIC을 구현하고 자동 검사와 브라우저 검사를 수행한다.
2. 사용자가 테스트할 수 있도록 브라우저를 열고 확인할 행동과 예상 결과를 한 번에 하나씩 안내한다.
3. `docs/05_테스트결과.md`에 자동 검사 결과와 사용자 직접 확인 결과를 구분해 기록한다. 실행 환경·확인 행동·예상 결과·실제 결과·문제와 수정·재검사 여부를 남긴다.
4. 구현·자동 검사 후 사용자 응답 전 상태는 ‘사용자 확인 대기’로 표시한다. 사용자 응답이 없거나 미확인 항목이 남으면 통과로 간주하지 않는다.
5. 발견된 문제를 수정하고 필요한 검사를 다시 수행한다. 사용자가 해당 EPIC을 문제없이 확인한 경우에만 이 문서의 EPIC 상태를 ‘완료’로 바꾼다.

배포나 계정 준비 등 외부 조건으로 수행하지 못한 검사는 미실행으로 기록하고 완료한 것으로 표시하지 않는다.
